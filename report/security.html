물음 1 · 서버가 어디에 있는가
「우리 데이터는
대체 어디에 저장되어 있나?」
답

데이터가 저장되는 곳과, 화면이 놓인 곳은 서로 다른 두 장소입니다.

화면(입구)은 검색에 노출되지 않아 링크를 아는 사람만 닿을 수 있고, 그 안에는 실제 숫자·이름이 없습니다. 데이터(내용물)는 구글이 운영하는 Firebase라는 잠긴 금고에 따로 있습니다.

🖥️
화면 (입구)
링크를 알아야 닿음 · 내용물 없음
색·글꼴·표의 '모양'만 담긴 빈 그릇. 검색에 뜨지 않아 링크를 아는 사람만 닿을 수 있고, 열어도 데이터는 나오지 않음.
화면 입구 (검색에 노출되지 않음)
🔒
데이터 (내용물)
구글 금고 · 잠김
매출·인사·채용. 구글 서버가 로그인·명단을 확인한 뒤에만 화면으로 내어줌.
Google Firebase (구글 데이터베이스)
비유
화면은 은행 건물, 데이터는 금고 속 현금입니다.

은행 건물 주소는 누구나 압니다. 하지만 주소를 안다고 금고가 열리지 않습니다. 금고에는 Firebase 접근 규칙이라는 '자물쇠'가 걸려 있고, 이 자물쇠는 gate 인증(로그인+허가 명단)이라는 '열쇠'를 가진 사람에게만 열립니다. 주소를 알아도, 자물쇠에 맞는 열쇠가 없으면 데이터는 나오지 않습니다.

물음 2 · AI와 구글에 맡긴 부분
「AI로 만들고 구글에 맡겼다는데,
그 판단은 왜 믿을 수 있는가?」
답

두 가지를 나눠 말씀드리겠습니다. AI는 만드는 '도구'였고, 구글은 지키는 '인프라'입니다.

AI는 대시보드를 빠르게 만들기 위해 쓴 도구입니다. 목수가 전동 공구로 집을 짓는 것과 같습니다 — 공구가 집을 소유하거나 지키는 것이 아니라, 사람이 설계하고 짓는 데 쓰는 것뿐입니다. 무엇을 어떻게 잠글지는 사람이 판단해 설계했고, AI는 그 지시대로 화면을 그렸습니다.

구글 Firebase는 그 데이터를 보관하고, 접근 규칙(자물쇠)을 거는 곳으로 택했습니다. 핵심은 '구글이라서'가 아니라, Firebase의 접근 규칙이 서버 단에서 강제된다는 점입니다 — 규칙에 맞지 않는 요청은 데이터에 닿기 전에 거부되므로, 주소를 알아내거나 코드를 뜯어보는 방식의 침입이 규칙 단계에서 막힙니다.

🔐 왜 Firebase인가 — 규칙이 '서버 안에서' 강제되기 때문

Firebase 잠금의 핵심은 접근 규칙이 사용자 쪽이 아니라 서버 안에서 판정된다는 점입니다. 보통의 허술한 방식은 '이 사람이 봐도 되나?'를 사용자 화면(브라우저)에서 확인하는데, 이러면 화면을 조작해 통과할 수 있습니다. Firebase는 그 판정을 서버 내부에서 수행하므로, 화면·코드를 아무리 뜯어봐도 규칙을 우회할 수 없습니다.

또한 규칙에 맞지 않는 요청은 데이터가 오가기 전에 거부됩니다. 흔한 침입 방식 — 주소를 알아내 직접 요청하기, 로그인 화면을 건너뛰고 데이터만 호출하기, 코드에서 접근 경로를 찾아내기 — 이 모두가 규칙 단계에서 막힙니다.

데이터를 내어줄지 말지는 우리가 설계한 접근 규칙이 서버 안에서 판정합니다. AI가 만든 화면은 이 판정에 관여하지 못하고, 금고 열쇠도 쥐고 있지 않습니다. 그래서 가장 민감한 열쇠(관리자 인증키)는 AI에게 전달하지 않습니다.

물음 3 · 주소만 알면 들어오지 않나
「주소(링크)만 알면
그냥 들어올 수 있는 것 아닌가?」
답

그 점을 인지하고 전면 개편했습니다. 지금은 세 가지가 겹칩니다 — ① 주소가 검색에 노출되지 않아 아는 사람만 입구에 닿고, ② 입구에 닿아도 구글 로그인을 해야 하며, ③ 로그인해도 허가 명단에 없으면 즉시 차단됩니다. 주소 하나만으로는 아무것도 열리지 않습니다.

개편 전

데이터를 시트에서 직접 읽던 방식
통제 지점이 화면·시트로 흩어져 있었음.

개편 후 (현재)

로그인 + 허가 명단 통과 필수
주소를 알아도 로그인·명단을 통과하지 못하면 데이터가 열리지 않음. 구글 서버가 강제.

🧪 대표적인 침입 경로를 점검하고 차단했습니다

말로 '안전하다'가 아니라, 외부 침입자가 흔히 시도하는 방법들을 직접 실행해 점검했습니다. 로그아웃(미인증) 상태에서 아래를 하나씩 시도했고, 모두 「권한 없음」으로 차단되는 것을 확인했습니다.

✕ 차단대시보드에 로그인 없이 직접 접속 — 잠금 화면만 뜨고 내부로 넘어가지 못함
✕ 차단로그인 화면을 건너뛰고 데이터만 호출 — 서버가 미인증으로 거부
✕ 차단데이터 주소를 직접 입력해 매출·원장 읽기 시도 — 규칙 단계에서 거부(permission-denied)
✕ 차단인사·채용 데이터 직접 호출 — 경영진 명단이 아니면 거부
✕ 차단명단에 없는 계정으로 로그인 — 접근 권한 없음 안내 후 자동 로그아웃

가장 흔하고 위험한 경로들을 점검한 결과, 매출·인사 자료 모두 이 방법들로는 열리지 않았습니다. 보안에 '완벽'은 없으므로, 앞으로도 새로운 위험이 확인되면 규칙을 계속 보완해 나가겠습니다.

🖥️ 로그인하지 않으면, 보이는 것은 이 화면뿐입니다

주소를 알고 들어와도, 등록된 계정으로 로그인하기 전에는 아래 잠금 화면에서 한 발짝도 넘어갈 수 없습니다. 데이터는커녕 대시보드 화면 자체가 열리지 않습니다.

🔒 미로그인 상태에서 대시보드 주소로 접속했을 때 — 로그인 전에는 이 벽만 보입니다

🚫 로그인에 성공해도, 명단에 없으면 튕겨 나갑니다

여기서 한 겹이 더 있습니다. 로그인 자체는 누구나 할 수 있지만(구글 계정은 누구나 있으니까요), 로그인에 성공해도 허가 명단에 이메일이 없으면 「접근 권한이 없는 계정입니다」라는 안내가 뜨고 몇 초 뒤 자동으로 로그아웃됩니다. 데이터는 물론, 대시보드 안으로 단 한 걸음도 들어오지 못합니다.

즉 잠금은 「로그인했는가」가 아니라 「허가 명단에 있는가」로 결정됩니다. 로그인은 신원 확인일 뿐이고, 실제 문을 여는 것은 명단입니다.

📋 그 명단(허가 명단)은 어떻게 관리되나

대시보드를 볼 수 있는 사람은 '허가 명단'에 이메일이 등록된 사람뿐입니다. 이 명단은 구글 금고 안에 별도로 보관되며, 명단에 없는 이메일은 앞서처럼 자동으로 차단됩니다.

입·퇴사에 따른 관리도 이 명단에서 이뤄집니다. 새 임직원이 오면 관리자가 이름(이메일)을 명단에 추가하고, 퇴사하면 명단에서 삭제합니다. 삭제하는 순간 그 사람은 로그인해도 즉시 차단되어, 더 이상 어떤 데이터도 볼 수 없습니다. 오늘 이경훈 이사를 추가한 것도 이 명단에 이메일 한 줄을 더한 작업입니다.

핵심 · 데이터 처리와 잠금 규칙
데이터를 어떻게 처리하고,
어떤 규칙으로 막았는지 쉽게 정리했습니다.

① 어디를, 왜 새로 잠갔는가

기존에는 데이터를 구글 시트에서 바로 읽어오는 방식이었습니다. 편리했지만, 화면의 로그인과 별개로 데이터 원본 쪽의 접근 통제가 느슨했습니다. 그래서 이번에 데이터를 시트에서 분리해, 구글이 규칙으로 지키는 금고(Firebase)로 옮기고, 그 금고에 「로그인 + 허가 명단」을 통과해야만 열리는 잠금을 걸었습니다.

핵심은 데이터가 드나드는 길을 하나로 좁히고, 그 길목을 구글 서버가 지키게 만든 것입니다. 아래에서 그 방법을 구체적으로 설명드립니다.

데이터가 드나드는 길이 이렇게 바뀌었습니다
📄전 — 화면이 시트에서 데이터를 직접 읽음 (통제 지점이 흩어져 있음)
↓
🔒후 — 화면은 구글 금고를 통해서만 데이터를 받음. 시트로 통하던 옛길은 닫음
↓
🪪금고는 로그인 + 허가 명단을 통과한 사람에게만 데이터를 내어줌

② 막은 방법 — 데이터를 '규칙이 지키는 금고'로 옮겼습니다

두 가지를 동시에 처리했습니다.

㉮ 데이터 원본을 화면이 직접 읽지 않게 바꿈 — 이제 화면은 시트를 직접 열지 않고, 구글 금고(Firebase)를 통해서만 데이터를 받습니다. 시트로 통하던 옛길을 끊었습니다.

㉯ 그 금고에 '접근 규칙'이라는 잠금 코드를 걸었음 — 「로그인했고, 허가 명단에 이름이 있는 사람에게만 데이터를 내어준다」는 규칙을 걸었습니다. 이 규칙이 없으면 금고는 아무것도 내주지 않습니다.

이 '접근 규칙'이 왜 확실한가
잠금 코드가 내 컴퓨터가 아니라 구글 서버 안에 있습니다.

보통 앱은 '이 사람 봐도 되나?'를 사용자 컴퓨터에서 판단합니다. 그러면 컴퓨터를 조작해 통과할 수 있습니다. 우리는 그 판단을 구글 서버 내부에 심었습니다. 데이터를 요청하면, 구글이 서버 안에서 「로그인했나 → 명단에 있나」를 직접 확인하고, 통과하지 못하면 데이터를 한 글자도 내보내지 않습니다. 외부인이 우리 코드나 컴퓨터를 아무리 뜯어봐도, 이 판단은 구글 서버 안에서만 일어나므로 손댈 수 없습니다.

③ 규칙(잠금 코드)은 어디에 있는가

이 규칙은 대시보드 화면 코드가 아니라, 구글 Firebase 프로젝트의 '보안 규칙(Security Rules)'이라는 곳에 별도로 저장·적용됩니다. 화면 코드를 통째로 복사해 가도, 이 규칙은 구글 서버에만 있어 함께 딸려 나가지 않습니다. 규칙을 바꿀 수 있는 사람은 프로젝트 관리 권한을 가진 회사 관리자뿐입니다.

그리고 마지막으로, 데이터 원본 시트의 공개 설정 자체도 「제한됨」으로 닫아 옛 우회 경로를 물리적으로 없앨 예정입니다. (현재 화면 전환은 완료, 시트 공개 차단은 마무리 단계)

④ 실제 잠금 규칙 (그대로 보여드립니다)

데이터를 지키는 실제 규칙을 그대로 보여드립니다. 아래는 구글 Firebase 서버에 등록된 잠금 규칙의 핵심이며, 파란 글씨가 각 줄의 뜻입니다.

// ── 매출·실적 데이터 ──
match /dashData {
  allow read: if 로그인함                 ← 로그인한 사람만
    && 허가명단에 이메일이 있음           ← 명단에 있어야 함
  allow write: if false;                 ← 아무도 못 고침(회사 서버만 기록)
}

// ── 인사·급여·채용 (경영진 전용) ──
match /execData {
  allow read: if 이메일 in [
    파운더, 엄현호, 신상준,               ← 이 5명
    김상현, 이경훈                           경영진만 열람 가능
  ];
  allow write: if false;                 ← 아무도 못 고침
}

핵심은 세 가지입니다. ① 로그인 안 한 사람은 첫 줄에서 막힘 · ② 명단(또는 경영진)에 없으면 그 다음 줄에서 막힘 · ③ 「고치기(write)는 아무도 불가」 — 데이터를 몰래 바꾸거나 지울 수 없고, 오직 회사 서버만 기록합니다. 이 판정은 전부 구글 서버 안에서 이뤄집니다.

잠금 구조
한 겹이 아니라, 네 개의 관문을 차례로 통과해야 합니다
데이터에 닿으려면 아래 네 관문을 모두 지나야 합니다. 하나라도 막히면 그 자리에서 멈춥니다.
1
주소(링크)를 알아야 함

대시보드 주소는 검색에 노출되지 않으며, 아는 사람만 접근할 수 있습니다. 주소를 모르면 입구 자체를 찾지 못합니다.

2
구글 로그인(본인 인증)

입구에 닿아도, 회사가 인정한 구글 계정으로 로그인해야 화면이 열립니다. 비밀번호 관리·부정 로그인 차단은 구글이 전 세계 계정에 적용하는 시스템을 그대로 씁니다.

3
허가 명단(Firebase 등록 이메일)

로그인에 성공해도, Firebase에 등록된 이메일이 아니면 「접근 권한 없음」으로 튕겨 나갑니다(자동 로그아웃). 로그인은 신원 확인일 뿐, 문을 여는 것은 이 명단입니다.

4
데이터 잠금 규칙 (구글 서버가 최종 강제)

앞의 셋을 통과해도, 데이터를 실제로 내어줄지는 구글 서버가 규칙으로 최종 판정합니다. 이 판정은 사용자 컴퓨터가 아니라 구글 서버 안에서 이뤄져 조작이 불가능하며, 민감도에 따라 또 나뉩니다 — 실적은 상담·웹마케팅까지, 인사·급여·채용은 경영진 5인만.

물음 4 · 소유와 승계
「지금 데이터가 담당자 개인 계정에 걸려 있는 것 아닌가?
담당자가 바뀌면 어떻게 되나?」
답

정확한 지적입니다. 현재 일부 데이터 원본이 담당자 개인 구글 계정에 연결되어 있는 것이 사실이며, 이는 소유·승계 측면에서 정리가 필요한 부분입니다.

그래서 이 보고와 함께, 계정·비밀번호를 파운더님께 이관하여 소유를 명확히 회사로 귀속시키고자 합니다. 데이터·인증·권한은 이미 구글의 회사 프로젝트 위에 있어, 담당자가 바뀌어도 시스템은 그대로 유지됩니다.

소유·승계 조치
소유는 개인이 아니라 회사입니다.
이를 '말'이 아니라 '계정 이관'으로 확정합니다.

· 데이터·인증·권한은 회사 구글 프로젝트에 귀속 — 담당자 PC나 사적 소유물이 아님
· 접근 권한은 명단으로 관리 — 입사 시 이름을 더하고, 퇴사 시 삭제 (오늘 이경훈 이사 추가도 이 방식)
· 담당자가 바뀌어도 데이터·명단·시스템은 회사에 그대로 남음

🔑 파운더님께 — 소유권 이관
  • 데이터 원본이 연결된 구글 계정 및 비밀번호를 파운더님께 전달
  • 파운더님은 이 계정으로 언제든 전체를 열람·통제·회수할 수 있음 — 시스템의 최종 소유·감독권이 회사에 있음을 실물로 확정
  • 일상 관리는 담당자가 대행하되, 열쇠(계정)의 주인은 회사임
📢 경영진 방 — 투명 공유
  • 대시보드 접속 링크와 오늘 이경훈 이사 권한 추가 내역을 경영진 방에 공유
  • 누가 무엇을 볼 수 있는지 경영진이 상시 확인할 수 있도록 공개 운영
한 장 요약

경영진께 드리는 답

✓화면과 데이터는 다른 장소 — 데이터는 Firebase의 접근 규칙(자물쇠)과 gate 인증(열쇠)을 통과해야만 열림.
✓AI는 만드는 도구일 뿐 — AI는 화면을 그리는 공구였고, 데이터는 우리가 설계한 접근 규칙이 서버 단에서 막아섭니다.
✓주요 침입 경로를 직접 점검 — 우회 접속·로그인 건너뛰기·데이터 직접 호출·비인가 로그인을 시도해 차단 확인. 새 위험은 계속 보완.
✓4단계 관문 — 주소 · 로그인 · 허가 명단 · 서버 규칙을 모두 통과해야 함. 실적은 상담·웹마케팅까지, 인사·채용은 경영진 5인만.
✓소유는 회사 — 이를 확정하기 위해 담당자 계정·비밀번호를 파운더님께 이관합니다.
본 문서는 경영진 대상 데이터 보안 보고 자료입니다.
기술 용어는 비유로 옮겼으며, 실제 구현은 업계 표준(구글 Firebase 인증·서버 접근 규칙)을 따릅니다.
